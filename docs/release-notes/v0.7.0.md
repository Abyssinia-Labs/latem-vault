## latem vault is now PinkVault

The command is `pinkvault`, with `pink` for short, and its directory is `~/.pinkvault`. It changes no store version and no protocol: devices on 0.5, 0.6 and 0.7 share a vault and sync with each other.

### Install

```sh
brew install abyssinia-labs/tap/pinkvault
```

For this release only, `latem-vault` and `openvault` still run PinkVault. Each says first, on stderr, that it is `pinkvault` now; the next release drops them.

### Coming from latem vault or openvault

Update latem to 0.14.0 or later first: it is the first latem that finds the vault in `~/.pinkvault`. Then, on each device:

```sh
pinkvault service install      # stops the old service, moves the vault, starts PinkVault's
```

It stops and removes the service under its old names (`dev.latem.vault.service` or `local.openvault.service` on macOS, `latem-vault.service` or `openvault.service` on Linux), and starts `com.abyssinialabs.pinkvault.service` or `pinkvault.service`, logging to `pinkvault-service.log`. On a Mac, macOS asks again whether pinkvault may use the local network: allow it, or this Mac can't sync.

Any other command moves the vault too, while no service runs for it. The move is one rename of `~/.latem-vault`, or of `~/.openvault` where that never moved, to `~/.pinkvault`, so the key file and the Secure Enclave keys go with it. It waits, keeps using the old directory and says why on stderr while an old service runs, while the Mac app from before PinkVault starts the service, while a latem older than 0.14.0 is installed, or while both `~/.latem-vault` and `~/.openvault` exist. In that last case, check which one is your vault, move the other out of your home directory, and run any `pinkvault` command.

`PINKVAULT_HOME`, `PINKVAULT_LOG` and `PINKVAULT_MDNS_SERVICE` replace the `LATEM_VAULT_*` and `OPENVAULT_*` variables, which are still read in 0.7 and go in the next release.

### Also

- **`service install` starts a Homebrew install through its `opt` link**, not the versioned keg that `brew upgrade` deletes, so the service keeps starting after an upgrade.

### What keeps the name openvault

The key-derivation contexts, the signature labels, the key file magics, the protocol IDs (`openvault/sync/1` and the rest) and the mDNS service `_openvault._udp`, pinned in `crates/crypto/src/frozen.rs`. They are part of every vault and of the wire, and nobody sees them.
